# Photos: Supabase Storage to Cloudflare R2

Goal: leave the Supabase Pro plan by moving photos to R2 behind `img.get-pinit.co.uk`, and load them faster.
Companion branch in `pinit-recommendations`: `photos-to-r2` (no git remote there yet).

## Decisions made
- Target the Supabase **Free tier** (accepting no daily backups, 7-day inactivity pause, 500 MB DB cap; DB is 393 MB).
- Location photos: **pre-generated WebP variants** (thumb 320 / card 720 / hero 1440) + the original, in R2. Avatars and covers: **Cloudflare Image Transformations** (not built yet).
- Photos are populated **on demand** when a location is opened, not by copying the whole bucket (see "Hook-up plan").
- Old app builds: no force-update gate.

## Measured facts (production, 2026-10-01)
- `location_photos`: 31,386 objects, 9.46 GB (mean 351 KB, median 59 KB; many sources are only ~400 px wide). `profile_photos` 373 objects / 43 MB. `collection_covers` 26 / 6 MB.
- 1,360 distinct locations appear in `user_location_actions` (9,970 photo objects, 4.4 GB).
- Variants on a 25-photo sample: thumb 19 KB, card 47 KB (median 32), hero 92 KB (median 32) mean. Variants never upscale, so small sources stay small.
- R2 cost at full migration: ~14 GB, ~125k write requests, about $0.06/month (R2 list prices from memory, constants in `scripts/migrate_photos_to_r2.py`).

## Built so far

### `pinit-recommendations` (branch `photos-to-r2`)
- `src/pinit/integrations/r2_photos.py`: variant generation and R2 upload. Key layout: `l/{id}/{n}_{thumb|card|hero}.webp`, `l/{id}/{n}_orig.{ext}`.
- `SupabaseService.upload_location_photo` writes R2 first, then Supabase while `PHOTO_DUAL_WRITE_SUPABASE` is true (default). R2 failure raises. Without R2 config it is unchanged.
- Both photo pipelines (`location_tasks.py`, `routers/proximal.py`) download 1600 px from Google when R2 is configured.
- `scripts/migrate_photos_to_r2.py`: resumable copy with `--dry-run`, `--limit`, `--only`, `--referenced-only`, `--verify`.
- Config: `secrets.py`, `.env.example`, `docker-compose.yml`, `deploy.sh` (R2 credentials bound from Secret Manager, never plain env).
- Tests: `tests/test_r2_photos.py`, `tests/test_migrate_photos_to_r2.py` (37 tests). The 8 failures in the wider suite also fail on `main`.

### `login` (this branch)
- `lib/utils/photo_urls.dart`: single source of truth for photo URLs. Inert until `PHOTO_CDN_BASE_URL` is set. `normalize()` rewrites legacy Supabase URLs.
- `lib/widgets/pinit_image.dart`: shared widget (variant by size role, `memCacheWidth`, shared 90-day disk cache, cream placeholder).
- `location.dart` resolves location photo URLs through one function; 4 call sites migrated to `PinitImage`; the `imageUrl ?? photoReference` fallback removed from those 4 files.

### Backfill state
`--referenced-only` run (9,944 photos, 12 workers) was started and had 0 failures at the last check. Verify with
`python scripts/migrate_photos_to_r2.py --verify` (from the recommender repo, R2 + Supabase env set).

## Hook-up plan: populate on demand

The app must never show a broken image while a photo is not in R2 yet, so the app keeps a legacy fallback until the server confirms R2 has it.

### Recommender
1. Move the copy logic in `migrate_location()` into `r2_photos.copy_from_supabase(location_id, index)` (download the legacy object, `upload_location_photo`). The script and the endpoint share it.
2. New `POST /locations/photos/ensure` with `{ "location_ids": [..] }` (max ~20), service role. Per id, in order:
   1. R2 `HEAD l/{id}/0_card.webp` exists: `ready`.
   2. Row has `image_stored` and the legacy object exists: copy primary plus `extra_photos_stored` extras into R2: `ready`.
   3. `image_unavailable`: `unavailable`.
   4. Otherwise publish the existing `photos` task (Google download, writes R2 and, while dual-write is on, Supabase): `pending`.
3. De-dupe concurrent calls with a short Redis lock per id (`cache_service.py` already provides Redis). R2 `HEAD` is a Class B request (10M/month free).
4. Add tests for each branch (mock R2 client and Supabase, same style as `tests/test_r2_photos.py`).

### Flutter
1. `RecommendationsApi.ensureLocationPhotos(ids)` next to `addLocationByGooglePlaceId` in `lib/services/recommendations_api.dart`.
2. A small `LocationPhotoEnsurer` service: batches and de-dupes ids, remembers `ready` ids for the session, notifies listeners when ids become ready.
3. Trigger it for rows with `image_stored == true` when a list is processed (`processLocationsWithImages`, `location.dart:325`) and, for extras, in `fetchExpandedCardPhotos` (`location.dart:~1708`).
4. `PinitImage.location` gets a `fallbackUrl` (the legacy Supabase URL). It shows the legacy URL until the id is `ready`, then switches to the CDN variant.
5. Delete the client-side Google download/upload code (`_downloadAndUploadImage`, `_downloadAndUploadExtraPhoto`, `_performImageDownload`, `photoMediaUriFor`). The server pipeline replaces it, which also removes Places API key use and the unresized 2000 px uploads from the app.
6. Avatars and covers: upload through a small Cloudflare Worker that verifies the Supabase JWT, then serve through `cdn-cgi/image`. Replace the remaining `Image.network` / `NetworkImage` sites with `PinitImage.avatar`.
7. Bump the startup snapshot version (`lib/services/startup_cache/`) so cached `_cache_image_url` values are re-derived.

Alternative considered: a Cloudflare Worker that fills R2 from Supabase on an R2 miss. No app change, but it needs Image Transformations per variant, so cost scales with usage. Rejected for flat cost; revisit if the endpoint approach proves awkward.

## Decisions needed
1. **Endgame for never-opened photos.** On-demand means photos nobody opens stay in Supabase, but the Free tier allows 1 GB, so the bucket must be deleted eventually. Options: (a) delete them after a grace period and let the Google pipeline re-fetch on first open (about $7 per 1,000 Places photo requests, from memory, only for photos that get opened); (b) run the full backfill before the downgrade (~$0 extra, 9.5 GB of Supabase egress, must happen before downgrading). Recommend (b) once, then delete the bucket.

## Before pointing the app at the CDN
- [ ] Cloudflare Cache Rule: do not cache 404 responses on `img.get-pinit.co.uk` (404s currently get a 4 h edge cache, so a photo requested before its upload would stay "missing"). Purge `/l/1/0_card.webp`.
- [ ] Remove `R2_*` keys from `login/.env` (it is bundled into the app as an asset). Only `PHOTO_CDN_BASE_URL` belongs there. Rotate the R2 secret if a build was made with it present.
- [ ] Create `r2-access-key-id` and `r2-secret-access-key` in Secret Manager and grant the Cloud Run service account access (deploy.sh stops with the commands if missing).
- [ ] Leave `PHOTO_DUAL_WRITE_SUPABASE=true` until installed apps no longer read Supabase URLs.
- [ ] Then: set `PHOTO_CDN_BASE_URL` in the app build, `--verify`, spot-check through the CDN, and measure image bytes per screen before and after.
